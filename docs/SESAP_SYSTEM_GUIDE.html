1Architecture — the end-to-end loop

One action in the app travels through orchestration and automation, writes to the system of record, and returns to the app as a visible change. The numbered arrows are the six hops below.

1App → Data Fabric

Creating or editing a ticket writes to the Ticket entity.

SDK entities API, Coded-App platform auth. New tickets land as Unassigned.

2App → Maestro

Acting on a ticket (create / resolve / close / escalate) starts the Maestro process for that action.

processes.start with the action + ticket context (Ref, Subject, Category, RiskLevel, ActorRole…) as input arguments, which drive the BPMN gateways.

3Maestro → RPA

The intake branch triages/routes, then a service task invokes the published robot.

Orchestrator.StartJob bound to release 38e6499b… in the SESAP-Live folder.

4RPA → AI & email

The robot asks Claude to categorise/prioritise/summarise/recommend, then emails via Gmail.

Anthropic call keyed by the Orchestrator asset SESAP_Anthropic_Key (never in the repo).

5RPA → Data Fabric

The robot assigns the ticket and writes AssignmentStatus from Unassigned → Assigned — the write-back that proves the loop.

Data Service activities update the record; UpdateTime advances (feeds the resolution-time KPI).

6Data Fabric → App

The app re-reads the entity and reflects the new status and assignee — trigger to visible result.

getAllRecords on load/refresh; the assignee name resolves back to an email so "Assigned To Me" works after reload.

Why the app also does the concrete work. Maestro can't write Data Fabric or send email directly, so the BPMN orchestrates and models the lifecycle while the robot and the app do the hands-on writes. Both are driven from the same app action, so what you see on screen and what the BPMN shows always agree.

5The RPA robot — TicketAutomation

One published robot with two modes, selected by whether an in_Stage argument is passed.

Mode A — lifecycle notification (in_Stage set)

Builds a branded HTML email for the stage (created / assigned / resolved / closed / escalated / sla / approval / approved / rejected) with the right colour, headline and copy, and sends it via Gmail — CC the supervisor on every message.

Mode B — batch auto-assign (no in_Stage) — invoked by Maestro

This is the write-back engine the orchestration calls:

StepWhat happens
1 · ReadQuery all tickets from the Data Fabric Ticket entity.
2 · KeyRead the Anthropic API key from the Orchestrator asset SESAP_Anthropic_Key (server-side, never in code).
3 · Triage (AI)For each Unassigned ticket, call Claude → category, priority, summary, recommendation. Falls back safely if the AI is unavailable.
4 · Route & assignMap category → team, pick the engineer, and write AssignedTo, Team, Category, Priority and AssignmentStatus=Assigned back to Data Fabric.
5 · NotifyEmail the requester ("your ticket has been assigned") and the assigned agent ("new assignment") — both CC the supervisor.

Step 4 is the write-back that closes the loop: AssignmentStatus goes Unassigned → Assigned, and the app reflects it on the next read.

8AI & Document Understanding

Two distinct AI capabilities.

Agentic triage (in the robot). When a ticket is created, the robot asks Claude to categorise, prioritise, summarise and recommend a resolution — and that decision drives routing and assignment inside the flow.

Document Understanding (in the app). Attach a document to the AI Copilot and it reads the contents: on-device OCR for images / ID cards (Tesseract), text extraction for PDFs (pdf.js), and direct read for text files — then it surfaces the detected amounts, dates, account numbers, references and a text preview. Both engines are lazy-loaded, need no API key, and degrade gracefully if a file can't be read.

9Roles, sessions & the safety toggle

Three roles, one codebase. Supervisor (admin) gets the command centre, approvals and all insight views; agents (each engineer) get a focused "my queue"; the customer gets a portal to raise and track their own requests. Every onboarded engineer has a login (username = first name, shared demo password).

Sessions. An active user stays signed in and survives reloads; after ~7 minutes of inactivity the session expires and the app returns to the landing page. Passwords are never shown on the login screen.

Live automation toggle (Settings). OFF by default so background actions don't consume Robot Units; turn it ON to fire Maestro, the robot and real emails for a live demo. The manual "Start Orchestration" control runs regardless.

Where the key lives. The Anthropic API key exists only as the Orchestrator asset SESAP_Anthropic_Key — never in the app, the repo, or the browser. The robot reads it at runtime.
